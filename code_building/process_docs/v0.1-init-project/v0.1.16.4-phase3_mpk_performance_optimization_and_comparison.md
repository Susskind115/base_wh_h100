# v0.1.16.4 — Phase 3: MPK Performance Optimization & SGLang Comparison

## 主题

MPK persistent kernel 在最优配置下的真实性能定位是什么？和 SGLang 的差距在哪里？SSP 的 serving capability（preemption）的 SLO 收益有多大？

## 动机

上轮 (v0.1.16.3) 完成了 SSP 协议的全部实现和正确性验证（prefix cache + preemption），但缺少：(1) SLO 层面的量化评测，(2) 和 SGLang 的公平性能对比，(3) MPK 配置优化空间的系统性探索。本轮目标：回答"MPK+SSP 相比 SGLang 有没有优势，优势在哪"。

## 实验 1: SLO 评测 — Preemption TTFT 改善

### 设计动机
验证 SSP Preemption 在 SLO 层面的收益：当高优先 request 在长 request 执行过程中"到达"时，TTFT 能改善多少？

### 实现方式
- 2 requests, Qwen3-8B, max_seq=512, page_size=64, batch=1
- Request 0 先执行（长 decode），CPU 通过 `progress_buffer` 观察进度
- 当 req 0 到达指定 progress 时，CPU 写 `preempt_signal=1` + `priority_override=1`
- GPU 在下一个 iteration boundary 暂停 req 0，admit req 1
- 测量 req 1 的 TTFT（从"到达"到首 progress > prompt_len）
- Sweep 到达时间：req 0 进度 25%/50%/75%
- 脚本: `codex_coding/auto_research/src/phase3/test_phase3_slo_eval.py`
- 结果: `codex_coding/auto_research/results/phase3/test_phase3_slo_evaluation.json`

### 命令

export NVSHMEM_LIB_PATH=$CONDA_PREFIX/lib/python3.10/site-packages/nvidia/nvshmem/lib

### 数据
| 场景 | Req 1 TTFT | Req 1 JCT | Req 0 JCT | Total time | TTFT 改善 |
|------|-----------|-----------|-----------|-----------|----------|
| Baseline (FIFO, 无抢占) | 2635ms | 5266ms | 2636ms | 5271ms | — |
| Preempt at 25% (step=128) | **14ms** | 2648ms | 5286ms | 5293ms | 188x |
| Preempt at 50% (step=256) | **14ms** | 2652ms | 5293ms | 5300ms | 188x |
| Preempt at 75% (step=384) | **14ms** | 2651ms | 5288ms | 5295ms | 188x |

### 结论
- **Preemption TTFT 恒定 14ms**，与到达时间无关（~190x 改善）
- 14ms = preempt 延迟 (~6.4ms, 1 iteration boundary) + req 1 首 iteration (~7.6ms)
- 总吞吐量几乎不变（+0.5%，5271→5300ms）
- Trade-off 清晰：低优先 req JCT 增加（被暂停时间），高优先 TTFT 190x 改善
- 论文图：X=arrival point, Y=TTFT。有抢占=14ms 水平线，无抢占=2635ms 水平线

## 实验 5: P0 — Split-KV Attention 启用

### 设计动机
发现 MPK 代码有 `paged_attention_split_kv_layer`（demo_hopper.py 中 `--split-kv-cache` flag）但 Qwen3Builder 默认未启用。当前 attention grid: (1, 8, 1) = 8 SMs。H100 有 128 worker SMs，120 个空闲。

### 实现方式
修改 `python/mirage/mpk/models/qwen3/builder.py`：

**新增 __init__：**
```python
self.num_kv_cache_chunks = max(1, mpk.max_seq_length // 256)
self.use_split_kv = (self.num_kv_cache_chunks > 1)
```

**新增 tensor（仅 split-kv 时）：**
```python
if self.use_split_kv:
    self.lse = self.mpk.new_tensor(
        dims=(max_batch_tokens, num_kv_cache_chunks * num_local_q_heads // num_local_kv_heads, num_local_kv_heads),
        strides=(...), dtype=float32, name="lse")
    self.attn_out_tmp = self.mpk.new_tensor(
        dims=(max_batch_tokens, num_kv_cache_chunks * num_local_q_heads // num_local_kv_heads * head_dim, num_local_kv_heads),
        strides=(...), dtype=bfloat16, name="attn_out_tmp")
```

**attention 层替换：**
```python
if self.use_split_kv:
    mpk.paged_attention_split_kv_layer(...)       # grid=(1, 8, 4) = 32 SMs
    mpk.paged_attention_split_kv_merge_layer(...)  # grid=(1, 8, 1) = 8 SMs reduce
else:
    mpk.paged_attention_layer(...)                 # grid=(1, 8, 1) = 8 SMs
```

### 命令
```bash

```

### 原始输出
```
P0 Split-KV: N=4,max_seq=1088,max_pages=48,pages_per_req=17
  num_kv_cache_chunks = max(1, 1088//256) = 4
Compiled OK
Starting kernel...
Total: 27150ms, output_tokens=4092, TPOT=6.635ms, throughput=151 tok/s
Compare: without split-kv was 6.90ms, SGLang was 6.48ms
```

### 数据

|------|------|--------------|
| 无 split-kv | 6.90ms | baseline |
| **有 split-kv** | **6.64ms** | **-3.8%** |

### 结论
- Split-KV 有效修复长序列退化：32 SMs 并行 vs 8 SMs 串行处理 KV

- 短序列（seq≤256）只有 1 chunk，自动退化为普通 attention，无额外开销

## 实验 6: page_size=128 + KV_TILE_SIZE=128

### 设计动机
page_size=64 → 每 request 17 pages，attention 每 tile 64 tokens（iteration 多，indirection 多）。增大到 128：pages 减半（9 pages）、attention tiles 减半、prefix cache 仍可用（最小可复用前缀=128 tokens，我们的 system prompt ~130 tokens → 1 page 可复用）。

### 实现方式

**CUDA 修改** (`multitoken_paged_attention_hopper.cuh:70`)：
```cpp
// 原始: constexpr int KV_TILE_SIZE = 64;
// 修改:
#ifndef MPK_KV_TILE_SIZE
#define MPK_KV_TILE_SIZE 64
#endif
constexpr int KV_TILE_SIZE = MPK_KV_TILE_SIZE;
```

**编译参数** (`persistent_kernel.py:288`)：
```python
kv_tile_size = getattr(mpk, 'kv_tile_size', mpk.page_size)
flags = flags + [f"-DMPK_KV_TILE_SIZE={kv_tile_size}"]
```

### smem 可行性计算
```
KV_TILE=64 (当前):
  Q: 8 tok × 4 QO_PER_KV × 128 dim × 2B = 8 KB
  K×2: 2 × (64 × 128 × 2B) = 32 KB
  V×2: 32 KB
  O accum: MMA_ITERS × 256 threads × 64 × 4B = 64 KB
  misc: ~4 KB
  Total: ~140 KB

KV_TILE=128 (新):
  Q: 8 KB (不变)
  K×2: 2 × (128 × 128 × 2B) = 64 KB
  V×2: 64 KB
  O accum: 64 KB (不变)
  misc: ~4 KB
  Total: ~204 KB

H100 smem limit: 207 KB → 204/207 = 99.4% 占用 → 可行但极限
```

## 实验 8: P2 — enable_online_softmax

### 排查过程
1. `enable_online_softmax` 定义在 `include/mirage/transpiler/structs.h:44`: `bool enable_online_softmax = false`
2. Python 侧暴露在 `generate_cuda_program()` 函数（`core.pyx:1311`），默认 `False`
3. 但 `generate_cuda_program()` 是 **transpiler 路径**（为自定义 operator 生成 CUDA 代码）
4. 我们使用 **pre-registered tasks** 路径：`kn_graph.generate_task_graph()` → 不走 transpiler
5. 我们的 attention kernel `multitoken_paged_attention_hopper.cuh` 已手动实现 online softmax：`s_m_buffer`（running max）和 `s_d_buffer`（running denominator）

### 结论
**不适用**。transpiler 路径专用，我们的 attention kernel 已内置 online softmax。

## 实验 9: bench_one_batch 对比（关键实验 — 论文对标方式）

### 设计动机
发现 MPK 论文的 SGLang baseline 用的是 `python -m sglang.bench_one_batch`（非 `bench_serving`）。bench_one_batch 直接跑 model engine，不经过 HTTP server，但**仍然启用 CUDA Graph**（从输出看到 "Capture piecewise CUDA graph... 10.89s"）。bench_one_batch 的 decode TPOT 比 bench_serving 高（引擎内调度开销更明显）。

### SGLang bench_one_batch 命令

## 实验 10: Cross-task pipelining 源码审计

### 设计动机
论文声称 cross-task pipelining 贡献 1.15-1.29x 加速（Figure 12, 最后一层 linear, B200）。为什么我们测不到论文的 1.6x？

### 论文描述
每个 task 分两个阶段：
1. **Pre-loading phase**: TMA 从 device memory 加载 weight 到 shared memory
2. **Compute phase**: WGMMA 矩阵乘法

Cross-task pipeline: 当 T1 的 compute phase 进行中（TMA 已完成），T2 的 pre-loading phase 可以同时启动 → T1 compute 和 T2 preload overlap。

### 排查方法和发现

**1. Transpiler 标记存在** (`src/transpiler/sched_tb_graph.cc:198`):
```cpp
op_meta.is_pipelined_input = op_meta.is_chunked_input &&
                             input_op->forloop_dim != -1 &&
                             config.target_cc >= GPU_CC::A100;
```
说明编译器知道哪些输入可以 pipeline。

**2. Runtime worker loop 无 overlap** (`persistent_kernel.cuh:870-910`):
```cpp
// Worker 主循环（简化）:
while (true) {
    fetch_task_descs();           // 从 queue 取 TaskDesc (cp_async 到 smem)
    wait_for_dependent_event();   // 等待前置 event counter
    _execute_task(task_desc);     // 执行完整 task（preload+compute 一起）
    __syncthreads();              // 全线程同步
    trigger_event();              // atomicAdd event counter
    // → 直接取下一个 task，没有 "在 T1 compute 阶段预加载 T2 weight" 的逻辑
}
```

**3. Linear kernel 内部有 intra-task pipeline** (`linear_swapAB_hopper.cuh`):
- `Kstages=2` 双缓冲 TMA pipeline（当前 tile compute 同时 prefetch 下一 tile 的 weight）
- 但这是同一个 task 内部的 pipeline，不是跨 task 的

**4. `SEQ_LEN_PER_BLOCK=256` 硬编码** (`task_register.cc:3336`):
```cpp
constexpr int SEQ_LEN_PER_BLOCK = 256;
```
这是 split-kv attention 的 chunk 大小，和 `num_kv_cache_chunks = max_seq // 256` 对应。

### 结论
**Cross-task pipelining 在开源代码中未实现。** 基础设施存在（is_pipelined_input 标记、paged smem）但 runtime worker loop 无实际 overlap 逻辑。**这是我们和论文数据差距的主要原因。**

实现需要：修改 worker loop 支持 "peek next task" + 为 linear task 添加 "early weight preload" 接口。预计 2-4 周高难度 CUDA 工程。

## 实验 12: Attention 实现分析

### MPK attention 架构 (`multitoken_paged_attention_hopper.cuh`)
- WGMMA (Hopper 原生矩阵乘法指令)
- TMA (Tensor Memory Accelerator, 异步 DMA)
- Paged KV cache (page_indices 间接寻址)
- Double buffer K/V (Kstages=2)
- Online softmax (s_m_buffer/s_d_buffer)
- 融合 RoPE + QK Norm 在 attention 内
- 2 warpgroups: 1 producer (TMA load) + 1 consumer (WGMMA compute)

### vs FlashInfer (SGLang 后端)
| 维度 | MPK | FlashInfer |
|------|-----|-----------|
| page_size | 128 (indirection) | 1 (实质连续) |
| Split-KV 策略 | 固定 max_seq//256 | 自动按 SM count |
| Kernel 调优 | 通用模板 | 手工极致调优 |
| Decode 模式 | WGMMA paged attention | Tensor Core decode |

### 结论
性能差距来自 kernel 实现质量（FlashInfer 手工调优 vs MPK 通用模板），不是 split 策略差异。追平 FlashInfer 需要重写 attention kernel（极高工程量）。

## 总结性结论

1. **SSP Preemption**: 14ms TTFT，190x 改善，overhead <2%，总吞吐不变
2. **MPK vs SGLang (offline/bench_one_batch)**: MPK decode 快 5-15%（0.6B 1.15x, 1.7B 1.10x, 8B 1.05x）
3. **MPK vs SGLang (online/bench_serving)**: 基本持平（Qwen3-8B: 6.49 vs 6.45ms）
4. **配置优化累计效果**: 长序列 TPOT 改善 5.1%（6.90→6.55ms）
5. **Cross-task pipelining 未实现**: 开源代码 runtime 无 overlap 逻辑，这是和论文数据差距的主因
6. **论文定位**: SSP 在 MPK decode 优势基础上增加 serving capability (prefix cache + preemption)，对标方式用 bench_one_batch 合理
