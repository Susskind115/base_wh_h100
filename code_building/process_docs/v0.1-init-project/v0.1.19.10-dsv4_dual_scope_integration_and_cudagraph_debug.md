# v0.1.19.10 — DSV4 Dual-Scope Fused Kernel 接入 + CUDA Graph 根因定位

## 主题

完成方向 3 的第一阶段落地：在 InfiniCore 中新建独立 op `dsv4_dual_scope_attention`，在 InfiniLM 的 DeepSeek V4 compressed decode 路径中接入 fused dual-scope kernel，并继续围绕 CUDA Graph crash 做控制变量定位。当前 eager decode 正确且提速，但 CUDA Graph 仍未最终打通；本轮已经把问题从“graph 总体 crash”缩到“compressed decode 路径在 self-replay 下仍不安全”，并进一步排除了 fused op 本身。

## 动机

v0.1.19.9 已经把 decode 路径优化到 ~210ms，但 compressed decode 仍然包含 CPU LSE merge / inverse RoPE，导致 `--enable-graph` 一定 crash。方向 3 的目标是在一个 fused kernel 中处理：

1. SWA scope（paged cache）
2. compressed scope（indexed blocks）
3. attention sink
4. inverse RoPE

这样理论上 decode 可以成为 100% GPU 路径，从而让 CUDA Graph 成为可能。

本轮不只是实现 fused kernel，还要严格按 `docx/debug_philosophy.md` 的控制变量原则，把 graph crash 的真正原因定位出来，而不是用猜测替代证据。

## 实验 5：路径判别 — crash 在 graph recording，不在 replay

### 设计动机

按 debug 哲学，先确认 crash 在哪一阶段：
- graph recording
- graph replay

### 实现方式

在 `paged_compiler.cpp` 和 `rank_worker.cpp` 中加最小路径日志：

- `capture_begin`
- `capture_forward_done`
- `capture_end`
- `replay_prepared`
- `replay_begin`
- `replay_end`

### 数据

原始日志关键片段：

```text
DSV4_GRAPH capture_begin batch=1
Switching device runtime during graph recording may break the graph!
DeepseekV4Attention: compressed layers (CSA/HCA) use LSE merge path for decode.
```

没有出现：

```text
capture_forward_done
capture_end
replay_begin
```

### 结论

- 第一阶段 crash 在 **graph recording**
- 不是 replay metadata copy 的第一主因

## 实验 6：修正 graph compile 的状态前提

### 设计动机

最初 graph compile 直接用“伪 decode 输入” capture，但 compressed decode 实际上需要合法的 prefill state。与此同时，`paged_attention_compressed_()` 还把所有 `query_len == 1` 路径误判成 decode。

### 修复 1：修正 decode 判定条件

把 compressed attention 的 decode 判定从：

```cpp
if (query_len == 1 && ...)
```

改成：

```cpp
if (query_len == 1 && inputs.query_start > 0 && ...)
```

也就是：
- 只有真正有历史 token 时才走 decode 路径
- `seq_len == 1` 的 prefill 不再误判成 decode

### 修复 2：graph compile 先做最小 prefill-state 初始化

在 `PagedCompiler::compile()` 中：
- 先构造 `prefill_input(past=0,total=1,pos=0)`
- eager 跑一次 prefill
- 再构造 `decode_input(past=1,total=2,pos=1)` 进行 graph capture

### 修复 3：补齐 graph 输入 metadata

补齐并在 replay 时 copy：
- `past_sequence_lengths`
- `compress_slot_ids`

### 结论

- graph recording 崩点被修掉
- capture 之后已经能走完大量 batch size 的图编译

## 实验 7：capture 后立即 self-replay（最关键的控制变量实验）

### 设计动机

区分真正问题是：
- runtime replay 输入和 capture 输入不一致（phase mismatch）
- 还是图自己一 capture 完就已经坏了（生命周期 / graph-safe 问题）

### 实现方式

在 `PagedCompiler::compile()` 里：
- `capture_end batch=1` 之后
- 直接 `graph->run()`
- 立即把 `output.logits` D2H

### 结果

**self-replay 直接失败，报 CUDA 700。**

日志：

```text
DSV4_GRAPH capture_end batch=1
DSV4_GRAPH self_replay_begin batch=1
Error Code 700 in cudaMemcpy(...)
```

### 结论

这是本轮最强证据：

- 还没进入真实 runtime replay
- 还没让真实 request metadata 介入
- self-replay 就已经失败

因此：

> **phase mismatch 不是当前第一主因。**

当前最像的根因是：

> **capture 录进图里的某些前向对象/状态路径本身就不 self-replay safe。**

## 当前最强结论（本轮核心）

把所有实验串起来后，当前最可信的判断是：

1. graph recording 初始 crash 已经修掉
2. replay metadata mismatch 不是当前第一主因（因为 self-replay 已经失败）
3. fused op 本身不是当前第一主因（因为 bypass fused op 仍然失败）
4. 当前最可疑区域已经收敛到：

> **compressed decode 的前半段增量状态推进路径整体不 self-replay safe**

更具体地说，是这条链：

```cpp
compressor_->decode_step(...)
  -> wkv_->forward(...)
  -> wgate_->forward(...)
  -> ring_pool.write(...)
  -> （后续状态推进 / graph 内部引用）
```

这条路径比普通 paged decode 多了一套“compressed state machine”：
- ring buffer
- overlap shift
- compressed block pool
- cached positions / cached seq_len
- valid_nb / indexer metadata

所以它不再只是“普通 KV cache append + attention”，而是一套更复杂的增量状态推进系统。

### 当前真正的阶段结论

> **DSV4 compressed decode 当前不能直接套用 InfiniLM 现有单图 decode CUDA Graph 范式。**
> **最先失败的不是 fused op，而是 compressed 增量状态推进路径整体在 self-replay 下不安全。**

---

## 为什么这个结论重要

这解释了两个问题：

### Q1. 为什么普通模型的 graph 原来可用？
因为它们主要依赖：
- compiler 持久输入
- GraphTensor 输出
- module workspace
- KV cache append

这些都是 InfiniLM 现有 graph-safe 范式已经覆盖的。

### Q2. 为什么 DSV4 看起来“数学上没本质不同”，但系统上会卡住？
因为它在普通 decode 之外多了一套 **compressed state update machine**：
- ring slot 由 `seq_len` 决定
- 周期性 shift / append block
- metadata 由当前状态动态推导

所以系统实现层面比普通 decode 明显更复杂。

## 附录 D：为什么“DSV4 看起来数学上没什么不同，但系统上会卡 graph”

这部分是专门给失忆后的自己、以及之后和用户讨论设计方案时快速恢复直觉用的。

### D.1 普通模型 decode 的状态机
普通 paged decode 主要只推进一套状态：
- paged KV cache append
- sequence lengths
- block tables

这套状态推进，InfiniLM 原有 compiler/graph 已经覆盖得比较成熟。

### D.2 DSV4 compressed decode 多了一套 compressed state machine
除普通 KV cache 外，还多了：
- ring buffer
- overlap shift
- compressed block pool
- cached positions / cached seq_len
- valid_nb / indexer metadata

所以它不是“普通 decode + 一个更复杂 attention kernel”，而是：

> **普通 decode + 第二套跨步演化的 compressed state machine。**

当前 graph 真正卡住的，正是这套 state machine 的 self-replay 安全性，而不是注意力公式本身。

## 附录 I：当前 graph-safe / graph-unsafe 对象清单

这节专门用于回答“哪些对象现在已经被我们处理成了持久对象，哪些还没有”。

### I.1 已经符合或部分符合 InfiniLM graph-safe 范式的对象

#### compiler 层
- `graph_input.input_ids`
- `graph_input.position_ids`
- `graph_input.past_sequence_lengths`
- `graph_input.total_sequence_lengths`
- `graph_input.input_offsets`

- `graph_input.block_tables`
- `graph_input.slot_mapping`
- `graph_input.compress_slot_ids`

这些都来自 `PagedCompiler::CompiledResult::input`，生命周期跨 compile / replay。

#### output 层
- `GraphTensor(output.logits)`
- replay 时 `resume_from_blob_()`

#### DSV4 attention 层（本轮新增）
- `graph_q_flat_`
- `graph_k_comp_`
- `graph_comp_positions_cpu_`
- `graph_comp_positions_`
- `graph_comp_indices_cpu_`
- `graph_comp_indices_`
- `graph_num_comp_blocks_cpu_`
- `graph_num_comp_blocks_`

这些已经不再是简单的 forward 局部 `Tensor::empty()`。

### I.2 仍可能 graph-unsafe 的区域

这里的“graph-unsafe”不是已经被证明错误，而是“还没被排除，且最值得继续怀疑”。

#### 1. compressed state update chain 内部状态推进
- `compressor_->decode_step()`
- `wkv_->forward()`
- `wgate_->forward()`
- `ring_pool.write()`
- （未来 step 里可能还有）`shift_overlap` / block append

#### 2. 非持久 view / contiguous 派生对象
即使底层内存来自持久 buffer，只要路径里仍然频繁出现：
- `narrow(...)->contiguous()`
- `view(...)->contiguous()`
- 以及一些前向中间结果重新 materialize

就仍然值得怀疑。当前第一轮 buffer 化还没有完全覆盖这类对象。

#### 3. 后续输出路径
因为 bypass fused op 之后仍然失败，所以问题也可能在：
- `apply_grouped_output_projection_()`
- grouped linear 路径
- graph 输出 blob 关联的某段前向对象生命周期

当前还没有做“完全绕过 compressed decode 但保留 output projection”的实验，因此这一层还没被完全排除。

## 附录 K：如果要继续做“分段绕过实验”，推荐的最小落地顺序

这一节不是结论，而是下一轮实现顺序建议。失忆后如果用户允许继续做分段绕过，直接按这个顺序推进。

### K.1 为什么不能再优先怀疑 fused op
因为：
- bypass fused op 之后仍然 self-replay 失败
- 所以 fused op 不再是最有信息量的切点

### K.2 最小顺序

#### Step K1：保持 compressed decode 外层形状不变，只跳过 `compressor_->decode_step()`
目的：先验证“只要不做 compressed state update chain，self-replay 是否恢复”。

如果 PASS：
- 直接说明问题在 state update chain 本身

如果仍 FAIL：
- 说明还要往 output / projection 路径继续查

#### Step K2：只恢复 `wkv_/wgate_`，不恢复 ring write
目的：区分问题在“线性投影”还是“状态写入”。

#### Step K3：恢复 ring write，但不恢复后续 block append / metadata 推导
目的：区分最先失效的是写 ring，还是更后面的状态衍生。

#### Step K4：最后再逐步恢复更后面的 state transition
例如：
- overlap shift
- block append
- 依赖 state 的 metadata 推导

### K.3 每一步必须坚持的原则
- 每次只改一个变量
- 每次先跑 self-replay
- self-replay 通过后，再去看真实 runtime replay
- 不要先去追 batch4，先把 batch1 self-replay 弄明白

## 附录 L：为什么这轮文档不能只写摘要

这轮最大的风险不是“代码量大”，而是**推理链容易断**。

如果只留下“graph 还是坏”“怀疑 compressed state update”这种摘要，失忆后会马上掉回下面这些错误方向：
- 再回头怀疑 fused op 本身
- 再回头怀疑 replay metadata mismatch
- 再重复排查 recording crash
- 不知道哪些实验已经做过，哪些已经被强证据排除

所以本轮过程文档必须保留：
1. 原始日志
2. 每一轮控制变量实验
3. 哪个假设已经被排除
4. 当前最可信假设是什么
5. 下一轮的最小实验序列

这也是为什么本轮归档要比普通“实现一个 op 并过 benchmark”的文档更长。它的价值不只是在记录“写了什么”，而是在记录“为什么现在应该相信这个判断，而不是另一个判断”。
